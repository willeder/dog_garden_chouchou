# 開発引き渡しドキュメント レビューと実装方針

作成日: 2026年8月16日
対象: `01_開発引き渡しドキュメント.md`（2026-08-16版）

---

## 0. 結論

**このまま着手できる完成度です。** 特に以下3つの判断は正しく、変更する必要はありません。

- `puppies` テーブルを作らず `dogs` に統合（自家保留がステータス変更だけで済む）
- 交配履歴の縦持ち（横36列の破綻を根本から解消）
- 計算値をビューに寄せて入力欄を作らない（仔犬検診日・次回交配可能月の検証も済んでいる）

一方で、**着手前に必ず解消すべき論点が3つ**あります。

| # | 論点 | 深刻度 | 理由 |
|---|---|---|---|
| A | **法令対応（帳簿・定期報告）が仕様に無い** | 高 | 今回のゴールとして「法令対応」を選択されたが、ドキュメントには要件が1行も無い。後付けするとスキーマ変更が発生する |
| B | **microCMS との二重管理** | 高 | 公式サイトの仔犬情報はすでに microCMS で運用開始済み。管理アプリでも仔犬を登録すると、同じ子を2箇所に入力することになる |
| C | **マイクロチップの正規化ルールが無い** | 中 | 実データの表記が不統一で、要件である「下4桁検索」が動かない |

以下、根拠と対処案を示します。

## 1. 論点A：法令対応が抜けている

### 何が必要か

第一種動物取扱業者（犬猫等販売業者）には、**個体ごとの帳簿を13項目・5年間保存**する義務があります。電磁的記録での保存が認められているため、このアプリがその帳簿そのものになり得ます。

さらに毎年**4月1日〜5月30日**に、前年度（4/1〜3/31）の実績を都道府県知事へ**定期報告**する義務があります。報告内容は種類ごとの集計で、

```
① 年度開始時点の所有数
② 新たに所有した数（繁殖・仕入れ）
③ 販売・譲渡・死亡した数
④ 年度末時点の所有数        ※ ①＋②－③＝④ が合うこと
```

### 現在のスキーマで足りないもの

| 法令上の記載項目 | 現在のスキーマ | 対応 |
|---|---|---|
| 品種等の名称 | `breed_code` | OK |
| 生年月日 | `birthday` | OK |
| 繁殖者の氏名**及び登録番号** | `partners.name` のみ | **登録番号のカラムが無い** |
| **所有した日** | 無し | **要追加**（②の集計に必須） |
| 入手先 | `supplier_id` | OK |
| 販売・引渡し日 | `sales.handover_date` | OK |
| 販売・引渡し先 | `customers` | OK |
| 引渡し先が関係法令違反でないことの確認状況 | 無し | **要追加** |
| 販売担当者名 | 無し | **要追加** |
| 対面説明等の実施状況 | 無し | **要追加** |
| **死亡した日・死亡の原因** | `status='死亡'` のみ | **日付も原因も持てない** |

### さらに構造上の問題：物理削除ができない

5年保存義務があるため、**行を物理削除すると保存義務違反になります。** 現在の DDL は

```sql
dog_id uuid not null references dogs(id) on delete cascade   -- vaccinations
```

となっており、犬を消すとワクチン履歴ごと消えます。論理削除に切り替えるべきです。

### 追加DDL案

```sql
-- 帳簿項目の追加
alter table dogs add column acquired_on   date;          -- 所有した日
alter table dogs add column died_on       date;          -- 死亡日
alter table dogs add column death_cause   text;          -- 死亡原因
alter table dogs add column deleted_at    timestamptz;   -- 論理削除（5年保存のため物理削除しない）

alter table partners add column license_no text;         -- 繁殖者の動物取扱業登録番号

alter table sales add column staff_name           text;  -- 販売担当者名
alter table sales add column explained_in_person  boolean default false; -- 対面説明の実施
alter table sales add column explained_on         date;
alter table sales add column compliance_checked   boolean default false; -- 引渡し先の法令違反確認

-- 物理削除の禁止（cascade を restrict に）
alter table vaccinations drop constraint vaccinations_dog_id_fkey;
alter table vaccinations add constraint vaccinations_dog_id_fkey
  foreign key (dog_id) references dogs(id) on delete restrict;

-- 定期報告用の年度集計ビュー（年度は4/1始まり）
create or replace view v_annual_report as
with fy as (
  select generate_series(
    date_trunc('year', (select min(coalesce(acquired_on, birthday)) from dogs)) ,
    date_trunc('year', now()), interval '1 year')::date as y
)
select
  b.code as breed_code, b.name as breed_name,
  f.fy_start, f.fy_end,
  count(*) filter (where d.acquired_on <  f.fy_start
                     and (d.died_on is null or d.died_on >= f.fy_start)
                     and not exists (select 1 from sales s
                                     where s.dog_id = d.id
                                       and s.handover_date < f.fy_start)) as opening_count,
  count(*) filter (where d.acquired_on between f.fy_start and f.fy_end)   as acquired_count,
  count(*) filter (where d.died_on     between f.fy_start and f.fy_end)   as died_count,
  count(*) filter (where exists (select 1 from sales s
                                 where s.dog_id = d.id
                                   and s.handover_date between f.fy_start and f.fy_end)) as sold_count
from (select make_date(extract(year from y)::int, 4, 1) as fy_start,
             make_date(extract(year from y)::int + 1, 3, 31) as fy_end from fy) f
cross join breeds b
left join dogs d on d.breed_code = b.code and d.deleted_at is null
group by b.code, b.name, f.fy_start, f.fy_end;
```

> 上記ビューは骨子です。実装時は実データで ①＋②－③＝④ が合うことを必ず検算してください。

### 「アラートは作らない」との整合

ドキュメントは通知・アラートを作らない方針ですが、**定期報告には5月30日という締切があります。** 通知は不要としても、

- `/admin/report` に「◯年度の定期報告」を表示し、①〜④の数字とCSV出力を用意する

これだけは必要です。プッシュ通知でもバッジでもないので、禁止事項#1・#2には抵触しません。

## 2. 論点B：microCMS との二重管理

### 現状

公式サイトの仔犬情報は **microCMS（`puppies` / `parents` / `voices`）で運用開始済み**です。すでに1頭登録され、サイトから読めることを確認しています。

この状態で管理アプリを「社内利用のみ」で作ると、**1頭の仔犬を microCMS と Supabase の両方に入力する**ことになります。写真も2回アップロードします。運用に乗りません。

ドキュメントの第11章6項が「着手前に決定すべき」としているのは、まさにこの点です。

### 選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| **B-1. Supabaseに一本化**（推奨） | 管理アプリを唯一の入力口にし、公開サイトは Supabase から読む。microCMS は `voices`（お客様の声）だけ残すか、廃止 | 二重入力ゼロ。すでに構築済みの microCMS 連携コードは差し替えになるが、API層（`_api/puppies/`）が分離済みなので影響範囲は限定的 |
| B-2. 管理アプリ → microCMS へ自動同期 | 公開ボタンで microCMS の Management API に書き込む | 同期のズレとエラー処理を一生抱える。おすすめしません |
| B-3. 併用（現状維持） | 社内台帳と公開情報を別々に入力 | 頭数が少ないうちは回りますが、必ず不整合が出ます |

### B-1を採る場合の追加要件

ドキュメント11-6に書かれている内容で正しいです。補足すると：

```sql
alter table dogs add column is_published boolean default false;

-- 公開してよい列だけのビュー（チップ・仕入れ元・価格・顧客は絶対に出さない）
create view v_public_puppies as
select id, breed_code, sex, name, birthday, color_code,
       expected_weight, price, message, photo_path
from dogs
where deleted_at is null and is_published = true and status in ('在舎','商談中');

-- 匿名ユーザーはビュー経由でのみ読める
create policy "anon_read_published" on dogs
  for select to anon
  using (is_published = true and deleted_at is null and status in ('在舎','商談中'));
```

写真の Storage は **公開バケットと非公開バケットを分けてください。** 同一バケットで公開制御すると、URLが漏れた時点で全件見えます。

## 3. 論点C：実データ由来の不具合（移行前に対処）

現行スプレッドシートを実際に読んで確認した内容です。ドキュメントの「変換ルール」に**書かれていない**ものだけを挙げます。

### C-1. 全角数字が混在している

```
ジョジョ 4回目: 「５８日　帝」   ← 全角
ジョジョ 5回目: 「58日　帝」     ← 半角
```

正規表現 `(\d+)日` では全角を拾えません。**変換前に NFKC 正規化（全角→半角）を必ず通してください。** カラー欄にも `ＢＫ`（全角）と `BK` が混在しています。

### C-2. 出産日が空で他の項目だけ埋まっている行がある

```
ジョジョ 2回目: 出産日=空 / 雄犬=クリフ / 62日　帝 / ♂2 ♀3
```

`litters.birth_date` は `not null` なので、このままでは投入できません。要確認リストに含めてください。

### C-3. 同一内容の重複行がある

```
ジョジョ 4回目 = 5回目 : 2026/5/21 クリフ 58日帝 ♂3 ♀1
クロミ   4回目 = 5回目 : 2026/4/30 クリフ 60日帝 ♂2 ♀2
```

コピー時の事故と思われます。**移行時に「同一母犬・同一出産日」の重複を検出して報告**してください。機械的に片方を消すと、本当に同日2回のケースがあった場合に事故になります。

### C-4. マイクロチップの表記が不統一（要件の「下4桁検索」が動かない）

```
392 149 002 433 081    ← 3-3-3-3-3 区切り
 392 146 001 717 375   ← 先頭に空白
392146 001 786 148     ← 区切り位置が違う
392149002175241        ← 区切りなし
```

対処：

- **保存は数字のみ15桁**（`regexp_replace(v, '\D', '', 'g')`）
- 表示時に `392 149 002 433 081` の形へ整形
- 検索は保存値に対する `like '%1234'` → これで下4桁検索が確実に動く
- `unique` 制約は正規化後にかける。**空文字ではなく NULL を入れること**（空文字が2件あると衝突する）

### C-5. カラーは7種類を大きく超える

ドキュメント11-4は「Phase 2の集計で判明する」としていますが、**先に数えました。超えます。**

```
AP / RD / BK / ＢＫ / BK T / CR / FN / W / ブラタン / CHLT /
マール / 牛 / 黒L / 白L / 茶L / 黒白L / チョコ白L / クリームL / ブラックタンL …
```

末尾の `L` / `S` は**ロングコート／スムースコート**（チワワの毛質）と読めます。毛色とは別の軸なので、`coat_type` として分離することを検討してください。混ぜると `coat_colors` マスタが破綻します。

### C-6. 台帳に存在しない犬が他シートに出てくる

ドキュメントが指摘する「琥珀」以外にも、「対象の犬」リストに**ビビ / みるく / ひまわり / ムム / マム / うる / ぷぷ** が並びますが、CI母犬台帳（19頭）に登録がありません。要確認リストに含めてください。

### C-7. 種雄犬に必須項目の欠落がある

TP種雄「アル」は誕生日・体重・マイクロチップ・カラーがすべて空です。`dogs.birthday` は nullable なので投入自体は通りますが、**帳簿の必須項目なので移行後に埋める必要があります。**

## 4. 論点D：監査ログが無い

3名が同じデータを読み書きし、かつ5年保存義務があります。「誰がいつ何を変えたか」が追えないと、数字が合わない時に原因を特定できません。

```sql
alter table dogs    add column updated_by uuid references auth.users(id);
alter table litters add column updated_by uuid references auth.users(id);
alter table sales   add column updated_by uuid references auth.users(id);
```

最小限これだけでも入れておくと、後から追加するより遥かに安く済みます。完全な履歴が必要なら `audit_log` テーブル＋トリガーですが、3名規模なら `updated_by` + `updated_at` で十分と考えます。

## 5. 論点E：Supabase のプラン選定

ドキュメントは Pro（$25/月）を前提としていますが、判断材料を整理します。

| | Free | Pro（$25/月） |
|---|---|---|
| DB容量 | 500MB | 8GB |
| ストレージ | 1GB | 100GB |
| バックアップ | 7日スナップショット | 日次バックアップ |
| **無操作時の一時停止** | **7日間DBリクエストが無いと自動停止**（手動再開が必要） | なし |

本件の規模（犬64頭・出産記録数百件）では**容量はFreeで足ります。** 判断の分かれ目は次の2点です。

1. **7日間の自動停止** — 毎日開く運用なら止まりませんが、年末年始や繁忙期の谷で止まる可能性があります。止まると手動再開まで誰も使えません
2. **バックアップ** — 5年保存義務のあるデータです。日次バックアップは保険として妥当

**Pro を推奨します。** ただし「$25はデータ消失リスクと停止リスクへの保険であり、容量のためではない」と理解したうえで契約されるのが健全です。写真を大量に入れる想定なら 1GB→100GB の差も効いてきます。

ドキュメントの Phase 1〜6 は妥当ですが、上記を踏まえて以下を提案します。

| Phase | 変更点 |
|---|---|
| **Phase 0（新設）** | **論点Bの決定**。Supabase一本化か併用かで、Phase 1のスキーマ（`is_published`・公開ビュー・Storage設計）が変わる。ここを決めずに進めると必ず作り直しになる |

| **Phase 7（新設）** | 定期報告画面（`/admin/report`）。年度を選ぶと①〜④とCSV出力 |

## 8. 評価できる点（変更不要）

批判ばかりでは判断材料になりませんので、**このまま踏襲すべき**と考える点も挙げます。

- **禁止事項12項目**：実務的です。特に #11（service_role キー）と #12（RLS）は事故が最も多い箇所で、明文化されているのは良い
- **紐の色による仔犬識別**：現場の運用をそのまま写す設計で、連番を振らない判断は正しい。これは台帳をよく観察していないと出てこない仕様
- **等幅フォントの機能要件化**：チップ番号15桁の照合を考えると装飾ではなく機能。同意します
- **計算値の検証を実データで済ませている**：仔犬検診＝出産日+49日、次回交配＝+5ヶ月の月初。母犬トトの4件で照合済みという記述は信頼できます
- **`dogs` 統合の根拠づけ**：「自家繁殖が多数存在する」という実データ観察から導いており、判断の理由が残っている
